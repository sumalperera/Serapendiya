# ADR-024 segmentation: decision packet in preparation

Status: **WORKING DRAFT; not an accepted format or implementation authority.**
This narrows the first segmentation decision in [ADR-024](ADR-024-storage-lifecycle-and-commit-proposal.md). It does not approve checksum changes, persisted indexes, deferred verification, retention or a commit coordinator.

## Existing boundary

At `c5617d3`, `src/storage.rs` uses one `segment-000000.log` and a version-2 checkpoint. A commit syncs segment data before replacing and syncing the checkpoint. Recovery verifies every frame in the certified prefix before truncating its uncertified suffix. The group limits are 1,024 batches and 16 MiB. Checkpoint generation is diagnostic, not proof of freshness. See [the recovery state proposal](ADR-004-recovery-state-proposal.md) for refusal and rollback limitations.

The intended first stage retains absolute offsets, existing frame and checksum coverage, full startup payload verification, immutable sealed segments, and rolling only between groups. The 128 MiB roll target is a target, not a hard limit: a whole supported group can take the active segment past it. No deletion is implied. Startup still scans all certified history; segmentation alone bounds neither startup time nor disk use.

## Decision requiring resolution

ADR-024 proposes both a manifest containing certified lengths and the existing checkpoint protocol. This must become one unambiguous atomic authority. Two candidates need review:

1. **Single replacement record:** a bounded manifest also acts as the checkpoint, identifying every segment and the active certified length and next offset. Each commit replaces it after syncing the active segment. Simple recovery authority, but rewriting metadata grows with segment count and needs an explicit bound and matched measurements.
2. **Separate topology and checkpoint:** the manifest records immutable sealed segments and the active identity; a checkpoint records the active certified boundary and binds to a specific manifest identity. Rolling must define which pair is authoritative at every rename and directory-sync interruption. This reduces per-commit metadata but adds a cross-file atomicity problem and potentially ambiguous valid pairs.

The working recommendation below selects candidate 1 for review; it is not accepted. In either case, no successful append can depend on unpublished topology; an error after publication begins can have an unknown outcome. A checksum-valid older record cannot establish freshness after rollback. A random identity alone does not provide fencing or rollback detection.

## Minimum recovery matrix for the selected protocol

All cases are evaluated under the cooperative lock and documented filesystem assumptions. Preserve ambiguous artifacts and refuse when the selected authority cannot prove a safe interpretation.

| Interruption or observation | Required result |
| --- | --- |
| New directory before initial authority is durably installed | Refuse ambiguous incomplete initialization; preserve artifacts. No append may have been acknowledged. |
| Group bytes written or segment synced, authority still certifies the old boundary | Verify all certified history first; only then may the active uncertified suffix be truncated and synced under the selected protocol. |
| New segment created or synced before topology publication | Old certified history remains authoritative. Preserve the extra file and refuse unless a separately reviewed classification proves a safe action. |
| Replacement authority written or synced but not published | Preserve temporary files; refuse open without mutation. Do not infer that their contents committed. |
| Authority renamed but directory sync fails or is interrupted | Outcome may be old or new after crash. Validate whichever durable state is observed; a returned error does not establish absence. |
| Published authority references missing, short, misordered or corrupt certified data | Fail closed; never recreate or truncate certified data. |
| Unknown version, extra file, unexpected link or conflicting identities | Refuse and preserve evidence; no filename alone proves disposability. |
| Sealed segment contains extra bytes or is modified | Require exact certified length and valid certified frames; refuse and preserve evidence on mismatch or detected corruption. |
| Authority is missing, corrupt, or an older valid copy is restored | Refuse missing/corrupt metadata; a coherent older valid copy is not distinguishable from a legitimate earlier state without an independent authority. |

## Compatibility and validation work remaining

The old single-segment layout must remain readable with its existing rules. A new reader must explicitly classify old and new layouts; a new layout must be rejected by old binaries without modification, verified against the actual old binary. Migration is an explicit offline copy to a distinct destination, with source preserved, full validation and offset/content comparison before any operator cutover. Interrupted destination creation must not affect the source. No automatic in-place conversion or downgrade is proposed.

Before asking for acceptance, review the candidate authority and complete its byte, directory, transition and refusal rules. Produce independently generated golden bytes for empty, multi-segment and migrated logs, plus malformed and future-version cases. Specify every create/write/sync/rename/directory-sync failure and deterministic tests, process crashes and separate ext4/XFS block replay. Plan tests for old-reader refusal, full-history payload corruption, offset continuity, oversized groups, orphan preservation and migration interruption. Define matched durability measurements for append latency and throughput, memory, rollover and full-scan startup at increasing segment counts. Existing G1 replay evidence does not validate this new protocol.

Reference research and the candidate specification are expanded below. They do not establish this protocol's correctness. No external implementation is being copied or dependency added by this draft.

Recommend one bounded replacement manifest as the **only** durable authority. This preserves the present reasoning: synced data precedes one published certified boundary. It avoids proving all combinations of two independently replaced files. The cost is rewriting O(segment count) metadata on every commit and a hard capacity limit; neither latency nor throughput improvement is claimed. At 4,096 segments the proposed maximum manifest is 98,356 bytes, versus today's 36-byte checkpoint. Full startup verification and the current derived in-memory index still scale with history. Candidate 2 deserves reconsideration if matched measurements show unacceptable metadata cost, but its cross-file transition must first have a complete safety proof and tests.

The per-commit manifest write is **52 + 24 × segment count bytes**, including its four-byte checksum: 76 bytes at one segment, 6,196 bytes at 256 and 98,356 bytes at 4,096, before filesystem write amplification and sync costs. No steady-state segment count has been established: without retention or compaction it continues to increase. The proposed 128 MiB target and 4,096-entry cap imply roughly 512 GiB of encoded log data at the target, not a fixed byte capacity or guarantee: group-boundary overshoot, empty active segments and configuration change the actual value, and payload capacity is lower due to framing. Once the cap is reached, an append requiring another roll must reject before mutation. Increasing the cap or adding fields requires a separately accepted format and compatibility decision; an explicit offline copy to a new destination is the proposed migration path, not an implemented v1-to-v2 procedure. Acceptance must record an intended workload/segment-count range, storage ceiling assumptions and the cost of metadata rewriting, or explicitly accept those as unresolved pending matched measurements. A smaller cap and larger target remain alternatives for review; neither is claimed superior without workload evidence.

## Candidate manifest v1 for review

This is a proposed, unaccepted format. Integers are unsigned big-endian; all arithmetic is checked. A manifest is exactly `52 + 24 * count` bytes, with count in 1..=4,096. The complete file is bounded before allocation or parsing. Reserved bytes must be zero. `manifest` is the sole authority; `manifest.tmp` is never an authority. Names and directory classification must make current binaries refuse the new layout before modifying it; verify with an actual old binary, not only by reasoning from source.

| Byte range | Field |
| --- | --- |
| 0..4 | ASCII `SRSM` |
| 4 | version 1 |
| 5..8 | zero reserved bytes |
| 8..12 | total encoded length, including checksum |
| 12..16 | segment count |
| 16..32 | nonzero 128-bit log identity, generated at initialization; diagnostic identity, not fencing |
| 32..40 | next absolute offset, at most `i64::MAX + 1` |
| 40..48 | diagnostic generation; checked increment, no freshness claim |
| 48..48+24*count | ordered entries, described below |
| last 4 bytes | CRC-32C of all preceding manifest bytes, encoded big-endian; same algorithm as existing checkpoints |

Each 24-byte entry is `base_offset: u64`, `end_offset_exclusive: u64`, `certified_length: u64`. Segment file names are `segment-` followed by the base offset as exactly 20 zero-padded decimal digits and `.log`. Entries start at offset zero and are contiguous: each base equals the preceding end; the final end equals manifest next offset. Every sealed entry is nonempty and has positive length; only the final active entry may be empty, and then its base equals its end and length is zero. Entries with duplicate names, invalid offset ranges, impossible lengths, trailing bytes, unknown versions, zero identity, invalid reserved bytes or bad checksum refuse. Exhausted offsets or generation reject new work before mutation; exhausted segment capacity rejects a group that requires a roll before mutation. A full segment limit is not permission to delete history. Verify decoded frames start at each entry's base and end exactly at its exclusive end and byte length. All existing frame bytes and checksums remain unchanged.

Writers derive the header's next offset from the final entry's exclusive end; readers derive it independently and refuse a mismatch rather than choosing between fields. A fresh log or a just-rolled active segment can be empty; a sealed segment cannot have equal start and end or zero length. The 24-byte entry has no reserved digest field. A seal digest, if separately accepted, needs a reviewed versioned format and migration or compatibility plan; this proposal does not allocate or implement it.

Generation is diagnostic only. There is exactly one authority name, `manifest`; `manifest.tmp` is never a candidate authority, even if its generation is greater. An unexpected second manifest or a stale temporary file causes refusal and preservation, including equal-generation conflicting bytes. **Do not select the highest generation**: a synced temporary record may never have been published, and a restored older valid authority cannot prove that a newer state did not exist. Generation comparison cannot resolve either case or establish rollback detection.

Temporary-file classification is for diagnosis only. It does not change the refusal rule or authorize cleanup:

| Observed temporary record alongside a valid authority | Proposed open behavior |
| --- | --- |
| Valid; generation greater than authority | Refuse and preserve both. The temporary record is not evidence of publication or a completed acknowledgment barrier. |
| Valid; same generation and identical bytes | Refuse and preserve both. Equality alone is not an approved cleanup protocol; review provenance and removal durability before considering an automatic repair. |
| Valid; same generation and different bytes | Refuse and preserve both as conflicting evidence. |
| Valid; generation lower than authority | Refuse and preserve both; do not infer a safe history from the number. |
| Invalid checksum, malformed, unreadable, unknown version, or authority missing/invalid | Refuse and preserve all artifacts; do not treat the temporary file as a replacement authority. |

A successful rename replaces the destination name and normally consumes the temporary name; an identical `manifest.tmp` alongside `manifest` is therefore not by itself proof of a crash between rename and directory sync. A failure around rename/directory sync can leave the old or new authority after recovery. An unacknowledged operation may have committed; retaining it is allowed when the surviving authority certifies it. The contract is that a successful ACK follows the complete durable barrier, not that every committed operation received an ACK.

An actionable operator recovery procedure must be reviewed alongside the refusal behavior before a release exposes this format. It must provide read-only inspection of both files and the referenced data, show identities, checksums, generations and certified ranges, retain a forensic copy, and require explicit operator action for any mutation. Do not offer an unqualified "publish temporary" operation: promoting an unpublished record would introduce a new commit protocol and could certify data without a justified recovery basis. A discard/quarantine procedure also requires a separately reviewed safety argument, file and directory sync ordering, failure handling and interruption tests; until specified and implemented, operator recovery remains an open release requirement, not an existing command. Inspection and repair must not silently overwrite or truncate certified data.

### Candidate operator procedure: isolate one temporary file

This is a proposed recovery operation, not an available command or permission to repair live data. Scope is intentionally limited to an existing, valid `manifest` and exactly one regular, singly linked `manifest.tmp`, with no extra segment, unknown entry, missing data, or invalid certified frame. It does not handle orphan segments, invalid authorities, initialization failures, ambiguous identity or restored rollback. Those cases require separate investigation; no generic repair is proposed.

1. Stop all writers and readers, take a verified offline backup, and obtain the same directory and lock-file exclusive cooperative locks as normal operation. Use descriptor-relative no-follow access. Read the authority and validate its entire certified history and sealed file lengths without any truncation, rename or deletion. Record file identities, lengths and content digests and report whether the active file has an uncertified suffix. If validation fails or the directory contains any other unexpected entry, stop and preserve everything.
2. Inspect the temporary file as bounded, untrusted bytes. Report validity and, where parseable, identity, generation, segment ranges and comparison to the authority. Never select a winner by generation. The tool exports both manifest byte streams and an inventory to an operator-selected evidence directory that is distinct from and outside the log directory. Create evidence files exclusively, sync their contents and evidence directory and its parent; report failure without modifying the log if this cannot be completed. Evidence may contain sensitive metadata, so access is restricted by the operator.
3. After an explicit operator selection of **quarantine temporary**, recheck the directory, lock and file identities and bytes against inspection. Atomically rename only `manifest.tmp` to a unique, non-overwriting quarantine name in the same log directory, then sync that directory. Never replace `manifest` or remove a segment. The quarantine name remains an unknown entry to ordinary open, deliberately keeping the log unavailable until it is moved outside the log. If an atomic no-replace rename is unavailable, refuse the operation; do not emulate it with a check-then-rename race. Any error or crash leaves the outcome uncertain and requires fresh inspection.
4. With locks still held, copy the quarantined bytes to a new file in the evidence directory, sync and verify the copy, then unlink the exact quarantined file only after rechecking its identity and content. Sync the log directory after unlink. No cross-filesystem rename is assumed. Any failed copy, verification, unlink or sync leaves the log unavailable or requires reinspection; never report success until the evidence copy and both directory updates are durable. Only then perform an ordinary reopen, which validates the full authority before any permitted active-suffix truncation. An error after unlink may leave the old or new directory state after crash; preserve and reclassify the observed state, never assume the unlink persisted.

This candidate explicitly discards the temporary file as an authority, while preserving its bytes outside the log. An operator must understand that an operation without an ACK may still have committed if the surviving `manifest` certifies it; conversely a temporary manifest cannot prove commitment. The procedure cannot reconstruct missing acknowledged data, detect coherent rollback, or resolve an orphan. The implementation must not expose the mutation until this procedure and its crash behavior are independently reviewed and accepted. A read-only inspection mode must work without first calling the normal opener, which refuses these states.

Interrupted quarantine itself needs a recovery path. The future inspection mode must enumerate unknown entries as untrusted evidence without following them and without requiring the normal directory classifier to accept them. It must report, without changing any file, the names, file types, identities, bounded content hashes and validation outcomes for the authority, temporary file, any quarantine-looking entry and the external evidence copy. A quarantine-looking name alone is never proof of origin or authorization to remove it. If a crash leaves a quarantine entry, if both temporary and quarantine entries exist, if the external copy cannot be verified, or if the provenance of any artifact is uncertain, stop and preserve all entries for investigation. The proposed automated operation does not resume or delete such an entry. This intentionally trades availability for a reviewable safety boundary; an independently reviewed resume procedure can be proposed separately. Normal open always refuses an unexpected quarantine entry.

The evidence requirement is byte-for-byte preservation of the entire temporary file, including malformed input. If its size is too large for the configured safe copying limit, unreadable, changes during copying, or cannot be copied and synced to an independent destination, refuse mutation; a truncated diagnostic report or a hash alone is not a forensic copy. Define the exact size bound and supported operating systems in the implementation review. The no-replace and directory-sync operations must be verified on each supported platform; neither cross-filesystem atomic rename nor uncooperative-process exclusion is assumed.

Required operator-procedure tests: deny mutation on each failed precondition; verify evidence contains exact original bytes and operator-selected path is outside the log; reject aliases and pre-existing quarantine/evidence names; test temporary files of every classification in the table, symlinks, multiple links and oversized files; inject failures and process death before and after every evidence write/sync, quarantine rename, directory sync, copy, verification and unlink; on restart ensure either the temporary or quarantined evidence is preserved, or the durable verified external copy exists. Verify the authoritative manifest and certified segment bytes never change. Test two concurrent operators and a running writer, lock loss, path replacement within the documented threat model, and permission/full-disk errors. Run block/VM replay for the mutation ordering separately from deterministic and process-crash tests. A release that cannot satisfy these conditions must document that operator mutation is unavailable and preserve the stopped log for investigation; it must not advertise automatic recovery.

The proposed roll target is configured in whole bytes from 1 MiB through 1 GiB inclusive, with a 128 MiB default. Values outside the range, including zero, refuse configuration before opening or mutating the log. This range is an operational limit, not an on-disk field or a measured performance recommendation. A different valid target may be selected on restart and affects only subsequent rolls; it cannot alter or reinterpret existing segments. A small target is permitted for constrained workloads and testing but reaches the segment-count cap sooner.

Before admitting a nonempty group, roll if the current active segment is nonempty and its certified length is already at least the target; otherwise append the whole group. Current admission limits remain 1,024 frames and 16 MiB of encoded group bytes. With those limits a segment can exceed the target by less than one maximum-sized encoded group; an empty active segment accepts the whole supported group even when that group exceeds the target. Never split a live append group. Existing segments created under a different target can be larger than this bound. Arithmetic and offsets must be checked before mutation. A full 4,096-entry manifest may still accept groups while its active segment is below the selected target; once a roll is required, reject the group before mutation. Segment entries are derived only from certified frames, never inferred from filenames.

## Proposed state transitions

Acquire the existing cooperative directory and lock-file locks, use directory-relative no-follow opens, and reject unknown entries, symlinks, nonregular files and multiply linked storage files under the existing threat model. Under the platform-specific durability assumptions, initialize an empty destination by creating and syncing its empty active segment and directory entry, then writing and syncing `manifest.tmp`, renaming it to `manifest`, and syncing the directory before returning a usable log. Incomplete initialization without an authority refuses and preserves artifacts. Parent-directory durability for a newly created directory follows the existing initialization protocol.

For an ordinary commit: validate all inputs and resource/offset bounds before any write; write the complete group to the active segment; sync that segment; write and sync a new `manifest.tmp`; rename it over `manifest`; sync the directory; only then publish offsets and return success. Any I/O failure after mutation starts latches the writer terminal. An error at publication can have an unknown outcome. A temporary file already present blocks writes and is preserved.

For rollover: after a completed group and before accepting a new group, exclusively create the next empty segment, sync it and the directory, then publish a replacement manifest that seals the former active entry and names the new empty active entry. Only after the manifest rename and directory sync succeeds may data be appended to the new segment. Rollover itself publishes no new offsets. If any operation fails, latch terminal and preserve artifacts. Generation increments for every published manifest, including rollover; its overflow is checked before creating the segment.

The ordering difference is deliberate: rollover must sync the new segment's directory entry before a durable manifest can refer to it. An ordinary append creates no segment entry; it syncs segment data, then syncs the replacement manifest and performs the rename followed by directory sync for publication. In both paths, a file sync alone does not make a new directory entry durable.

If a crash occurs after segment data sync but before manifest publication, those bytes may be durable yet remain uncertified under the observed old authority; recovery may remove the suffix only after verifying the certified history and resolving artifacts as specified. A caller observing an error or timeout cannot infer that the append did not commit. There is no universally available reconciliation path in G1: reading a range only helps when the caller has a trustworthy way to identify the operation, and retry is safe from duplication only with a separately specified durable idempotency contract. Such a contract and native outcome-query interface are future decisions; preserve the [roadmap's unknown-outcome limitations](../roadmap.md#planned-end-to-end-workflow) and do not promise that every unknown can be resolved.

Future error reporting should consider an attempt identifier, assigned offset range and completed sync stages, but only when actually known and with clear meaning and access controls. A segment-sync result does not establish manifest publication, and assigned offsets or a client-supplied request ID do not prove identity or durable deduplication. The current protocol does not persist a request-to-outcome mapping or guarantee these details survive a crash; future APIs cannot promise that today's unknown outcomes will be resolvable. Define and test those semantics separately before exposing them.

On open, validate the entire directory and the authority first, then validate **all** certified frames and cross-segment continuity before any truncation. Each sealed file must have exactly its certified length; an active file may have a suffix only after the entire certified history validates. Truncate only that active suffix and sync the file; if truncation or its sync fails, refuse. A recognized `manifest.tmp` is preserved and causes open to refuse without truncation or other mutation; it cannot be treated as evidence of a committed boundary. Any extra segment, including one left by interrupted rollover, causes refusal with no mutation. Missing, short or corrupt certified data, unexpected sealed suffixes and inconsistent authority also refuse. A valid older manifest plus a coherent older history remains indistinguishable from rollback.

For every segment create, segment sync, directory sync, temporary create/write/sync, rename and final directory sync, test failure before and after the operation, partial writes, process death and relevant reordered persistence. The observed old or new manifest may govern recovery only if all referenced certified data validate; an orphan makes recovery refuse. A failure after rename or a failed directory sync does not prove the prior manifest persisted. A failed create or sync may leave artifacts requiring inspection. Preserve them rather than inventing a repair procedure.

## Proposed offline migration and cutover

Migration is an explicit operator action on a stopped partition, with exclusive cooperative locks held throughout the copy and comparison. Resolve source and destination by directory handles and identity; reject identical directories, aliases and nested destinations. The destination must be newly created and empty, on a separately chosen path. Never overwrite an existing destination or modify source data. Acquire locks in a deterministic identity order, and refuse if either lock cannot be obtained. The operator must stop old and new writers and retain a verified backup; cooperative locks do not constrain uncooperative writers or external restores.

1. Validate the complete source under its existing checkpoint protocol and record its checkpoint bytes, certified offset and certified length. Refuse stale temporary artifacts or uncertified source suffixes: migration must not repair the source as a side effect. Read only the certified prefix and preserve frame bytes and offsets.
2. Initialize the new destination using the proposed durability protocol. Copy whole frames in order, group them only at frame boundaries, and roll between groups. Publish each destination boundary only after syncing its data. Verify the complete destination using a fresh read-only validation pass, compare every source and destination frame byte-for-byte and confirm the final offset and frame count. Recheck the source authority and identity before reporting success; any mismatch aborts.
3. Sync all destination files and its directory and ensure its parent directory entry is durable. Report both identities and the verified end offset. Stop with both directories intact; the operator changes the configured path while all writers remain stopped. Reopen and validate the destination before resuming writes. Preserve the source as a rollback artifact; once new writes occur, switching back loses them and is not an automatic rollback.

An interruption or failed comparison leaves the source authoritative and the destination incomplete or untrusted. No automatic cleanup is allowed. Operators inspect and quarantine that destination under a distinct name only after confirming no process has it open; create a fresh destination for a retry. A successful destination may contain fewer copied records at an intermediate certified boundary; existence of a valid manifest alone is not migration completion. Completion requires the comparison report and explicit cutover. The detailed command interface, safe exclusive destination creation, identity checks and implementation tests remain to be specified and reviewed.

### Migration boundary proposed for review

The migration command operates on existing source and destination **parent** directories and a single destination name. Open parents without following symlinks, resolve and lock the source directory and its existing `.lock` using the same order as the current reader, and retain those descriptors through verification. Check that the source layout is legacy, its files are singly linked regular files, its checkpoint is valid, its segment length equals the certified length, and no temporary or unknown entry exists. The normal `Log::open` cannot serve as this read-only check: it may truncate an uncertified suffix. A dedicated non-mutating validation path is required. Record source directory and file device/inode identities, exact checkpoint bytes and full certified content; identity is an alias check, not a freshness or fencing guarantee.

Before creating a destination, preflight the complete certified source using the selected valid roll target and the destination's 4,096-entry limit. Simulate copy in offset order using **one existing frame per migration group**: original append-group boundaries are not persisted and must not be invented. Start with one empty active segment; before each frame, if the simulated active length is nonzero and at least the target, create the next simulated segment, then add the entire frame length with checked arithmetic. Do not create an extra empty segment merely because the final frame reaches the target. An empty source requires one empty segment. Validate every frame using the legacy format and supported size bounds, check offset continuity and count all required segments. If validation, arithmetic, format support or capacity fails, report failure before destination creation and leave the source untouched. This scan does not reserve disk space or prove later I/O will succeed.

If preflight would exceed 4,096 entries, refuse migration without silently omitting data, deleting history or changing the chosen target. The operator may explicitly choose a larger valid target and repeat preflight; if no valid target fits, migration under this candidate format is unavailable and requires a separately reviewed format or lifecycle decision. Report required segment count, selected target and certified source length before copying. During copy follow exactly the preflight grouping and rollover decisions, verify frame lengths and identities again, and abort if observations differ; hold the source lock and preserve the source throughout. Since the destination must remain offline until full comparison and explicit cutover, intermediate destination commits do not claim to reproduce the original group boundaries or expose a partial migration to clients.

Boundary cases for the future tests: target minus one byte followed by an oversized supported frame remains in the current segment; the next frame triggers a roll; exactly target triggers a roll before the next frame; the final frame reaching target does not create a trailing empty segment; an empty source creates one empty active segment; exactly 4,096 required entries is accepted by preflight, 4,097 is rejected before destination creation. Cover changing a target across restart, maximum-sized groups, overflow, unsupported source frames and I/O failure after successful preflight. Verify source bytes and identity remain unchanged in every case.

On 2026-11-13, a standalone arithmetic sketch of the proposed preflight was checked for those seven empty, target-boundary, oversized-group and 4,096/4,097 cases; all assertions passed. This was not an independent implementation, did not parse frames, model filesystem faults or exercise the production code, and does not constitute migration validation. The sketch's count alone must never authorize cutover; the real procedure still validates every frame and performs the full post-copy comparison.

The destination parent must be outside the source tree and the source outside the destination tree. Compare identities by walking descriptor-relative parent chains to their roots; if ancestry cannot be established, a mount or alias makes the result ambiguous, or a name can be redirected under the supported threat model, refuse. Create the destination name exclusively with `mkdirat`; an existing name, including a symlink, is an error. Open the resulting directory without following links, check its identity, lock it, and sync the parent entry before creating storage files. Never adopt an existing empty destination. This proposal assumes trusted directory ancestry and cooperative storage users; hostile concurrent renames, bind-mount aliases and non-cooperating writers require additional defenses and are not ruled out by a pathname comparison. If a safe identity/ancestry check is unavailable on a target platform, refuse migration there.

An intermediate destination can be internally valid but incomplete. Therefore it must not be exposed to normal service discovery or configured as a partition during migration. There is no automatic completion marker in manifest v1: after copy, a successful command emits a report containing source and destination identities, source checkpoint bytes, counts, final offset and a digest of each complete certified byte stream. The report is an operator aid, not an independent durability authority; equality is established by a full byte-for-byte comparison while both locks remain held. Re-read and compare source checkpoint, file identities and content after destination verification; fail on any change. Report success only after destination and parent syncs. The operator records the report outside both storage directories and separately switches the configured path while writers remain stopped. If the report is lost, rerun a complete offline validation and comparison; never infer completion from the destination manifest alone. The precise CLI syntax is intentionally left to implementation, but it must expose distinct source, destination parent and new destination name, return nonzero for incomplete or uncertain completion, and never perform cutover.

The comparison and cutover assume the operator keeps both directories offline between verification and configuration change. The tool cannot guarantee that assumption after its locks are released. If the source changes, either directory is replaced, or destination writes occur during that interval, repeat verification under locks before cutover. Cleanup or quarantine is an explicit operator action after preserving evidence; no automated deletion is specified.

### Proposed interruption matrix

Every row requires before-operation, after-operation and error-return injection, plus short writes where applicable. Process termination and block replay are separate exercises. No result is accepted solely because an injected API call returned success: recovery uses only the durable artifacts actually observed.

| Phase and interruption | Observable state and required behavior |
| --- | --- |
| Initialization: destination mkdir or parent sync | No success; absent directory may be retried with a fresh name. If an entry exists or durability is uncertain, preserve it and treat it as incomplete. |
| Initialization: lock/segment create, segment sync or directory sync | No success. A nonempty directory without a valid authority refuses opening and is preserved; no prior append was acknowledged. |
| Initialization: manifest temporary create/write/sync | No success. Preserve temporary or partial artifacts. Missing authority or a temporary manifest causes refusal. |
| Initialization: rename or final directory sync | No success on error; after crash the authority may be present or absent. Open only a complete valid state with no ambiguous artifacts; otherwise refuse and preserve. |
| Append: data write or segment sync before temporary creation | Writer latches terminal on error. On restart, validate the entire old certified history before truncating and syncing only an uncertified active suffix; no returned success covers this group. |
| Append: temporary create/write/sync | Writer latches terminal; preserve any temporary manifest. If it exists on restart, refuse without truncation. If absent, the valid old manifest can authorize recovery of only its certified prefix. |
| Append: rename or directory sync | Returned error has unknown outcome. Old or new authority may survive; validate observed authority and all referenced data. Refuse on temporary artifacts or inconsistent certified data. A successful return requires the final sync. |
| Rollover: new segment create, file sync or directory sync | No new offsets are committed. If an unreferenced segment survives, refuse and preserve it; otherwise the old authority remains usable after complete validation. |
| Rollover: temporary manifest create/write/sync, rename or final directory sync | Refuse if a temporary or orphan survives. Otherwise validate whichever authority survived; a valid new authority includes the empty active segment, and the old authority cannot justify accepting an extra file. No write enters the new segment before the rollover barrier succeeds. |
| Migration: any destination initialization, copy, publication, verification or final sync | No completion report on failure. Preserve destination; source bytes, checkpoint and identity remain unchanged. A valid partial destination is still incomplete and cannot be selected for cutover. |
| Migration: after report, before or during manual cutover | Both paths remain intact. Revalidate if either could have changed; a configuration switch is an operator action, not a storage atomicity guarantee. Never silently fall back after destination writes. |

Fault tests must snapshot names, content, identities and certified offsets before and after each refusal, and assert that no acknowledged frame is lost or changed. Inject active-suffix truncation and truncation-sync failures after a fully validated prefix; both must refuse rather than claim recovery succeeded. Include exhausted generation and capacity before mutation, a failed rollover followed by attempted append, and stale manifests paired with otherwise valid files. Each test records whether its model is an API fault, process crash, or actual replay; reordered persistence is a storage-model assumption to validate with replay, not a process-kill result.

### Decision and evidence boundaries

The decision requested for the first segmentation stage must enumerate the manifest v1 bytes and limits, rollover and refusal rules, full-history verification, unknown append outcomes, supported filesystem assumptions and explicit offline-copy compatibility. It must also record that 128 MiB and 4,096 segments are provisional workload assumptions and that per-commit manifest cost has not yet been measured. Human acceptance of these specified decisions is required before implementing them; acceptance does not by itself approve the operator mutation candidate above, persisted indexes, deferred verification, a coordinator, retention, or G1 acceptance.

The release of a segmentation implementation requires the specified implementation-level tests and operator workflow to be reviewed and available, or an explicitly accepted operational limitation for cases that cannot be repaired. New-format process crash tests and ext4/XFS block/VM replay are post-implementation evidence, not prerequisites that can be run against a proposal. Passing them would not itself establish independent review, universal device behavior or G1 acceptance. If implementation or replay exposes an unsafe state, stop and revise the proposal rather than treating this packet as proof.

Before requesting the format decision, the following design work remains open: review the complete fixture corpus; independently review the proposed target bounds, migration preflight and ancestry rules, and operator quarantine procedure on supported platforms; and decide the initial operating/workload envelope or explicitly record that it remains unvalidated. These are not implementation tests and must not be reported as complete.

The current code uses ordinary replacement rename for checkpoint publication and does not provide the proposed no-replace quarantine operation. No supported-platform no-replace and directory-durability capability matrix has been established; implementation must fail closed on unsupported targets and cannot claim cross-platform operator recovery until tested. The ancestry proposal also assumes trusted parent paths and cooperative locks; directory-handle walks do not by themselves rule out all mount aliases or hostile renames. The conservative answer for unresolved aliasing is refusal, with explicit target-platform tests and review before use.

### Filesystem primitive review, 2026-11-13

The pinned rustix 1.1.6 source exposes `renameat_with` and `RenameFlags::NOREPLACE`; its platform-specific definitions map the flag to Linux `RENAME_NOREPLACE` and Apple's `RENAME_EXCL`. The [Linux rename manual](https://man7.org/linux/man-pages/man2/renameat2.2.html) says no-replace support depends on the underlying filesystem; it lists ext4 and XFS support subject to kernel/filesystem versions. [Apple's volume capability documentation](https://developer.apple.com/documentation/foundation/urlresourcekey/volumesupportsexclusiverenamingkey) likewise describes exclusive rename as a volume capability. API availability does not establish runtime filesystem support or crash durability. Return an error on unsupported operations; do not substitute a check followed by replacement rename.

On the local Darwin 25.6.0 ARM64 host, the standalone [C probe](../verification/adr024-rename-probe.c), compiled with `clang -Wall -Wextra -Werror`, created disposable files under `/private/tmp`, observed `EEXIST` for an exclusive rename onto an existing file with its contents intact, successfully renamed to an absent name, and observed a successful directory `fsync`. This is an API behavior check only: it is not the Rust integration, a concurrent rename test, a process-crash test or a power-loss replay, and it does not prove persistence of the directory change. No Linux runtime test or macOS power-loss claim follows. A release matrix still needs ext4/XFS tests, platform-specific failure handling and the operator procedure's crash tests.

## Matched measurement protocol

Use the same machine, filesystem and mount options, compiler, release settings, payloads, group sizes and synchronous ACK boundary for baseline and candidate. Record commit IDs, environment, free space, warm-up, run order, raw samples, errors and sync counts. Alternate order across at least five independent fresh-log runs per configuration. Measure append group throughput and p50/p99/p99.9 latency, sync duration and counts, CPU and peak RSS, fetch latency, rollover pause and full-verification reopen time. Use enough samples for the reported percentiles; otherwise report sample counts and omit unsupported tails. Include group sizes 1 and 16 and payloads 32 B, 1 KiB and 64 KiB, plus segment counts 1, 16, 256 and 4,096 where feasible. Compare at matched total history as well as increasing history; report the baseline's single-segment topology explicitly. Record setup time and disk requirements; label infeasible combinations rather than extrapolating. The existing macOS repair benchmark is historical context, not a candidate comparison.

No performance threshold is currently approved. Present absolute results and candidate/baseline ratios with run-to-run spread for review before deciding whether the manifest rewrite cost is acceptable. Do not infer improvement from a synthetic metadata measurement.
